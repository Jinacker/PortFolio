# 아키텍처 의사결정 — 왜 이렇게 설계했나

돈가스 지도는 서비스 특성상 순간적인 대규모 동시접속이 많은 서비스는 아니고, **1인 개발·운영 서비스**이기 때문에 복잡한 인프라보다 **안정적으로 오래 관리할 수 있는 구조**를 우선했습니다.

현재 필요한 만큼은 단순하게 구성하되, 앱·지도·관리자 웹처럼 **변경 주기가 다른 영역은 분리**하고, 트래픽이나 기능이 커졌을 때 자연스럽게 확장할 수 있도록 경계를 잡았습니다.

## 1. 백엔드는 하나로, 책임은 명확하게

현재 규모에서는 서버를 여러 개로 나누기보다 **배포·모니터링·장애 대응 지점을 줄이는 것**이 중요하다고 판단했습니다.

백엔드는 NestJS 단일 서버로 운영하되, **앱과 관리자 웹의 API·비즈니스 로직을 모듈 단위로 명확히 분리**했습니다. 서버는 하나지만 사용자용 기능과 관리자용 기능이 뒤섞이지 않도록 책임과 변경 범위를 나눴고, 인증·식당·커뮤니티·알림 등도 도메인별 모듈로 구성했습니다.

인프라는 **Cloud Run**을 사용해 서버 관리 부담을 줄이고, 사용량에 따라 자동으로 확장할 수 있도록 했습니다.

> **NestJS Monolith + Domain Module · Cloud Run**

## 2. 자주 바뀌는 지도는 앱에서 분리

지도는 맛집 추가, 클러스터링, 권역 표시 등 **서비스에서 가장 자주 개선되는 화면**입니다.

Kakao Maps 기반 지도를 별도의 웹으로 구성하고 React Native 앱에서는 WebView로 불러오도록 했습니다. 덕분에 **스토어 심사 없이 지도 기능을 바로 수정·배포**할 수 있습니다.

구버전 앱도 안정적으로 사용할 수 있도록 지도 웹을 버전별로 운영하고 있으며, 향후 웹 서비스로 확장할 때도 기존 지도를 그대로 활용할 수 있도록 구성했습니다.

> **Kakao Maps Web + React Native WebView**

## 3. 운영 기능은 별도 관리자 웹으로 분리

맛집 등록, 푸시 발송, 방문 통계, 문의 관리처럼 반복되는 운영 업무를 위해 **별도의 React 관리자 웹**을 만들었습니다.

실제 서비스를 함께 운영하는 파트너도 사용할 수 있도록 구성했고, 앱과 독립적으로 배포해 **제품 릴리즈와 관계없이 운영 기능을 빠르게 수정하고 개선**할 수 있도록 했습니다.

> **React Admin SPA · Independent Deployment**

## 4. 기존 사용자와 데이터를 깨뜨리지 않는 변경

실사용자가 생긴 뒤부터는 새로운 기능을 추가하는 것만큼 **기존 앱과 데이터를 안전하게 유지하는 것**이 중요해졌습니다.

PostgreSQL은 Prisma로 관리하고, Cloud Run의 인스턴스 증감에 대응하기 위해 **pgbouncer 기반 Connection Pooling**을 적용했습니다.

DB 스키마도 기존 필드를 바로 삭제하거나 변경하기보다 새로운 구조를 추가하는 **additive migration**을 기본 원칙으로 두었고, 현재까지 **25회의 마이그레이션을 파괴적 변경 없이 진행**했습니다.

## 5. 지금은 단순하게, 확장은 필요한 순간에

처음부터 Redis나 Queue 같은 구조를 모두 도입하기보다, 현재 서비스에 필요한 수준으로 유지하고 있습니다.

대신 서비스가 성장했을 때의 다음 선택은 미리 정해두었습니다.

**트래픽 증가 → Redis 공유 캐시 · Queue 기반 비동기 처리**  
**이미지 업로드 증가 → Presigned URL 직접 업로드**  
**웹 서비스 확장 → 기존 Kakao Map Web 재사용**

처음부터 복잡한 구조를 만드는 것보다, **지금은 단순하고 안정적으로 운영하면서 필요해지는 순간 자연스럽게 확장할 수 있는 구조**를 목표로 설계했습니다.
