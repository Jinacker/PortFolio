# 아키텍처 의사결정 — 왜 이렇게 설계했나

돈가스 지도는 서비스 특성상 순간적인 대규모 동시접속이 많은 서비스는 아니고, **1인 개발·운영 서비스**이기 때문에 복잡한 인프라보다 **안정적으로 오래 관리할 수 있는 구조**를 우선했습니다.

현재 필요한 만큼은 단순하게 구성하되, 앱·지도·관리자 웹처럼 **변경 주기가 다른 영역은 분리**하고, 서비스가 성장했을 때 자연스럽게 확장할 수 있도록 경계를 잡았습니다.

## 1. 백엔드는 하나로, 내부 책임은 명확하게

현재 규모에서는 서버를 여러 개로 나누기보다 **배포·모니터링·장애 대응 지점을 줄이는 것**이 더 중요하다고 판단했습니다.

백엔드는 **NestJS + Prisma 기반 단일 API 서버**로 운영하되, 앱과 관리자 웹의 기능이 뒤섞이지 않도록 **사용자용 API와 관리자용 API를 구분**하고, 인증·식당·세션·커뮤니티·알림 등도 도메인별 모듈로 나눴습니다.

인프라는 **Cloud Run**을 사용했습니다. 요청량에 따라 자동으로 확장되고, 유휴 시 인스턴스가 0까지 줄어드는 **scale-to-zero**를 활용해 서버 관리 부담과 사용하지 않는 시간의 비용을 함께 줄였습니다.

> **NestJS Monolith · Domain Module · Cloud Run**

## 2. 가장 자주 바뀌는 지도는 앱에서 분리

지도는 서울에서 전국으로 확장하고, 클러스터링·권역 표시·시점 조회 등을 계속 개선하면서 **서비스에서 변경 주기가 가장 짧은 화면**이 됐습니다.

그래서 Kakao Maps 기반 지도를 별도 웹으로 구성하고 React Native 앱에서는 WebView로 불러오도록 했습니다. 덕분에 **지도 수정마다 App Store·Play Store 심사를 다시 받지 않고 웹 배포만으로 반영**할 수 있습니다.

또한 구버전 앱이 새로운 지도 변경으로 깨지지 않도록 **3가지 버전을 동시에 서빙하고 기존 URL은 유지**하고 있습니다.

> **Kakao Maps Web · React Native WebView · Versioned Deployment**

## 3. 운영 기능은 별도 관리자 웹으로 분리

맛집 등록, 푸시 발송, 방문 통계, 문의 관리처럼 반복되는 운영 업무를 위해 **별도의 React 관리자 웹**을 만들었습니다.

실제 서비스를 함께 운영하는 파트너도 사용하는 도구이기 때문에 앱과 별도로 배포해, **제품 릴리즈와 관계없이 운영 기능을 빠르게 수정하고 개선**할 수 있도록 했습니다.

공유 링크의 OG 처리처럼 웹에서 따로 필요한 기능 역시 Vercel의 Serverless Function으로 분리해 API 서버와의 배포 결합을 줄였습니다.

> **React Admin SPA · Vercel · Serverless Function**

## 4. 기존 사용자와 데이터를 깨뜨리지 않는 변경

실사용자가 생긴 뒤부터는 새로운 기능을 추가하는 것만큼 **이미 설치된 앱과 기존 데이터를 안전하게 유지하는 것**이 중요해졌습니다.

PostgreSQL은 Supabase에서 운영하고, Cloud Run의 인스턴스 증감에 대응하기 위해 **pgbouncer 기반 Connection Pooling**을 적용했습니다.

DB 스키마도 기존 필드를 바로 삭제하거나 의미를 바꾸기보다 새로운 구조를 먼저 추가하는 **additive migration**을 기본 원칙으로 두었습니다.

현재까지 **25회의 마이그레이션을 파괴적 변경 없이 진행**했습니다.

> **PostgreSQL · Supabase · pgbouncer · Additive Migration**

## 필요한 순간에 자연스럽게 확장할 수 있도록

처음부터 Redis나 Queue 같은 구조를 모두 도입하기보다 현재 서비스에 필요한 수준으로 유지했습니다.

대신 서비스가 성장했을 때의 다음 선택은 미리 정해두었습니다.

**트래픽·인스턴스 증가 → Redis 공유 캐시 · Queue 기반 비동기 처리**

**사용자 이미지 업로드 증가 → 서버 검증 구조를 유지하면서 직접 업로드 방식 검토**

**웹 서비스 확장 → 기존 Kakao Map Web 재사용**

처음부터 복잡한 구조를 만드는 것보다, **지금은 단순하고 안정적으로 운영하면서 필요해지는 순간 자연스럽게 확장할 수 있는 구조**를 목표로 설계했습니다.
