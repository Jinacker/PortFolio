# 5분인 줄 알았던 캐시가 0.3초였습니다 — TTL 단위를 바로잡아 목록 응답을 0.253초에서 0.101초로 줄였습니다

> 주석과 실제 캐시 동작이 다른 원인을 설치된 라이브러리 코드에서 확인하고, 캐시 대상과 만료 시간을 다시 정한 뒤 배포 환경에서 효과를 측정했습니다.

## 한눈에

| | |
|---|---|
| **발견** | `@CacheTTL(300)`을 5분으로 사용하고 있었지만 실제로는 0.3초 뒤 만료됐습니다. |
| **원인** | 현재 설치된 라이브러리는 TTL을 초가 아니라 밀리초로 전달하고 있었습니다. |
| **수정** | 밀리초 단위를 코드에 명시하고, 필요한 조회 API만 캐시하며 데이터 변경 시 캐시를 비우도록 했습니다. |
| **결과** | 목록 응답은 0.253초에서 0.101초, 상세 응답은 0.292초에서 0.089초로 줄었습니다. |

## 주석과 실제 동작이 달랐습니다

캐시 설정을 점검하던 중 `@CacheTTL(300)` 옆에 5분이라는 주석이 남아 있는 것을 확인했습니다. 하지만 현재 설치된 `@nestjs/cache-manager` 3.x와 `cache-manager` 7.x에서는 이 값이 밀리초로 전달되고 있었습니다. 의도한 5분이 아니라 0.3초만 캐시되고 있었습니다.

448KB인 맛집 목록 응답도 0.3초 뒤에는 다시 데이터베이스에서 조회됐기 때문에 캐시 효과를 거의 얻지 못하고 있었습니다.

설치된 라이브러리 코드와 기존 설정을 함께 확인해 세 가지 문제를 찾았습니다.

| 확인한 내용 | 실제 동작 |
|---|---|
| **TTL 값** | `300`이 변환 없이 전달돼 300밀리초로 처리됐습니다. |
| **Redis 설정** | 라이브러리는 `stores`를 읽지만 기존 코드는 `store`를 반환해 설정이 적용되지 않았습니다. |
| **캐시 범위** | 컨트롤러 전체에 적용돼 검색처럼 캐시가 필요하지 않은 조회까지 포함됐습니다. |

## 운영에서 Redis가 사용됐는지도 확인했습니다

Redis 설정 오류가 실제 운영에 영향을 줬는지 확인하기 위해 서버 시작 로그를 살펴봤습니다. 운영 환경에는 Redis가 없었고, 모든 연결 시도는 `ECONNREFUSED 127.0.0.1:6379`로 끝난 뒤 메모리 캐시를 사용하고 있었습니다.

처음에는 Redis 연결 시도가 서버 시작을 늦추고 있을 가능성도 생각했습니다. 그러나 로그의 시각을 대조하니 연결 거부는 0.1밀리초 안에 끝났습니다. 따라서 이 연결 시도는 시작 지연의 원인에서 제외했습니다.

```mermaid
flowchart LR
    A["주석은 5분<br/>실제 값은 300"] --> B["설치된 라이브러리<br/>코드 확인"]
    B --> C["300밀리초로<br/>처리됨을 확인"]
    C --> D["운영 로그로<br/>Redis 미사용 확인"]
    D --> E["TTL과 캐시 대상을 수정"]
    E --> F["같은 URL을 두 번 호출해<br/>저장 전후 응답 측정"]
```

## 필요한 조회만 캐시하도록 바꿨습니다

| 변경 | 내용 |
|---|---|
| **단위 명시** | `MINUTE` 상수를 사용해 밀리초 단위임을 코드에 드러냈습니다. |
| **만료 시간 조정** | 목록 1분, 상세 2분, 정적 데이터 5분으로 시작했습니다. |
| **대상 축소** | 컨트롤러 전체가 아니라 공개 데이터 조회 API에만 적용하고 검색은 제외했습니다. |
| **변경 내용 반영** | 관리자가 맛집을 등록·수정·삭제하면 캐시를 비우도록 했습니다. 캐시 삭제가 실패해도 데이터 변경 자체는 막지 않습니다. |
| **불필요한 설정 제거** | 실제로 사용되지 않던 Redis 분기와 의존성을 제거해 관련 코드를 204줄 줄였습니다. |
| **재발 방지** | TTL이 밀리초 기준 1분 이상인지 확인하는 항목을 포함해 테스트 14개를 작성했습니다. |

기존에는 사실상 실시간이던 응답이 이제 설정한 시간 동안 유지되므로, 관리자 변경 직후 오래된 데이터가 보이지 않게 하는 처리가 중요했습니다. 쓰기 작업이 끝나면 캐시를 비우도록 해 이 문제를 줄였습니다.

## 배포 환경에서 같은 URL을 두 번 호출했습니다

![캐시 수정 전후 실측](/assets/experiences/katsu-map/capture-09-cache-drift.svg)

| 조회 | 첫 호출 | 캐시된 두 번째 호출 | 차이 |
|---|---:|---:|---:|
| **맛집 목록 448KB** | 0.253초 | **0.101초** | 0.152초 감소 |
| **맛집 상세** | 0.292초 | **0.089초** | 0.203초 감소 |

측정 환경의 왕복 지연은 약 0.08초였습니다. 따라서 두 번째 호출은 서버에서 추가로 처리한 시간이 매우 작았고, 수정한 캐시가 실제 배포 환경에서도 사용되고 있음을 확인했습니다. 서버 시작 로그에서 Redis 연결 시도가 사라진 것과 배포 후 1시간 동안 오류가 0건인 것도 함께 확인했습니다.

## 남은 한계

- 1~5분의 만료 시간은 데이터 신선도를 우선해 보수적으로 정한 값입니다. 더 늘리려면 운영 응답 시간과 변경 빈도를 함께 확인해야 합니다.
- 현재는 데이터가 바뀌면 관련 항목만 골라 지우지 않고 캐시 전체를 비웁니다. 캐시 대상이 늘어나면 항목별로 지우도록 바꿀 필요가 있습니다.
- 메모리 캐시는 서버 인스턴스끼리 공유되지 않습니다. 여러 인스턴스를 운영하게 되면 실제 Redis 저장소를 연결해야 합니다.
