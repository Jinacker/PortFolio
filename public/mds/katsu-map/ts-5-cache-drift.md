# 잘못 설정된 캐시 만료 시간을 바로잡아 응답 속도를 개선했습니다

> 주석과 실제 캐시 동작이 다른 원인을 설치된 라이브러리 코드에서 확인하고, 캐시 대상과 만료 시간을 다시 정한 뒤 배포 환경에서 효과를 측정했습니다.

## 한눈에

| | |
|---|---|
| **발견** | `@CacheTTL(300)`을 5분으로 사용하고 있었지만 실제로는 0.3초 뒤 만료됐습니다. |
| **원인** | 설치된 라이브러리에서 TTL 값이 밀리초 단위로 처리되고 있었지만, 기존 코드는 이를 초 단위처럼 사용하고 있었습니다. |
| **수정** | 밀리초 단위를 코드에 명시하고, 필요한 조회 API만 캐시하며 데이터 변경 시 캐시를 비우도록 했습니다. |
| **결과** | 같은 URL을 연속 호출했을 때 목록은 253ms→101ms, 상세는 292ms→89ms로 캐시 사용을 확인했습니다. |

## 5분 캐시가 실제로는 0.3초 만에 사라지고 있었습니다

코드에서는 `@CacheTTL(300)`을 **5분 캐시로 사용하고 있었지만, 실제로는 300ms 뒤 만료**되고 있었습니다. 설치된 라이브러리 코드를 확인해보니 현재 버전에서는 TTL 값이 밀리초 단위로 전달되고 있었고, **주석과 실제 동작이 달랐습니다.**

448KB인 맛집 목록도 0.3초가 지나면 다시 데이터베이스에서 조회돼, **반복 조회를 줄이기 위한 캐시 효과를 거의 얻지 못하고 있었습니다.**

## TTL뿐 아니라 캐시 적용 범위도 다시 확인했습니다

| 확인한 문제 | 영향 |
|---|---|
| **TTL 단위 불일치** | 의도한 분 단위가 아니라 0.3~1.8초 만에 캐시가 만료됐습니다. |
| **캐시 범위가 너무 넓음** | 검색처럼 요청 조합이 다양하고 실시간성이 필요한 조회까지 캐시되고 있었습니다. |
| **변경 후 무효화 필요** | TTL을 늘리면 관리자 수정 직후 이전 데이터가 남을 수 있었습니다. |

### 현재 운영 규모에 맞게 캐시 구성을 단순화했습니다

초기에는 Redis 기반 캐시도 고려했지만, 현재 트래픽 규모에서는 **별도 Redis를 운영하는 비용과 복잡도보다 인메모리 캐시가 더 적합하다고 판단**했습니다. 이번 점검 과정에서 과거 Redis 설정이 남아 서버 시작 시 불필요한 연결 시도를 만들고 있는 것도 확인해, **사용하지 않는 설정과 의존성을 제거하고 현재 운영 방식에 맞게 캐시 구성을 단순화**했습니다.

## 필요한 조회만 캐시하도록 바꿨습니다

| 변경 | 내용 |
|---|---|
| **단위 명시** | `MINUTE` 상수를 사용해 밀리초 단위임을 코드에 드러냈습니다. |
| **만료 시간 조정** | 목록 1분, 상세 2분, 정적 데이터 5분으로 시작했습니다. |
| **대상 축소** | 컨트롤러 전체가 아니라 공개 데이터 조회 API에만 적용하고 검색은 제외했습니다. |
| **변경 내용 반영** | 관리자가 맛집을 등록·수정·삭제하면 캐시를 비우도록 했습니다. 캐시 삭제가 실패해도 데이터 변경 자체는 막지 않습니다. |
| **재발 방지** | TTL 단위와 캐시 적용 범위를 확인하는 테스트를 추가했습니다. |

캐시 수명을 분 단위로 늘리면 관리자 변경 직후 이전 데이터가 남을 수 있습니다. 따라서 **TTL 수정과 쓰기 후 캐시 무효화를 함께 적용**했고, 캐시 삭제가 실패하더라도 식당 데이터 변경은 정상 반영되도록 두 작업을 분리했습니다.

## 배포 환경에서 캐시가 실제로 동작하는지 확인했습니다

배포 후 동일 URL을 연속 호출해 **첫 요청은 `MISS`, 두 번째 요청은 `HIT`가 발생하는지 확인했습니다.**

![캐시 수정 후 첫 호출과 캐시된 두 번째 호출의 응답 시간 비교](/assets/experiences/katsu-map/capture-09-cache-drift.svg)

| 조회 | 첫 호출 `MISS` | 두 번째 호출 `HIT` | 차이 |
|---|---:|---:|---:|
| **맛집 목록 448KB** | 253ms | **101ms** | 152ms 감소 |
| **맛집 상세** | 292ms | **89ms** | 203ms 감소 |

목록은 253ms→101ms, 상세는 292ms→89ms로 줄어 **수정한 캐시가 실제 배포 환경에서도 재사용되고 있음을 확인했습니다.** 이 수치는 서로 다른 배포의 전후 성능을 비교한 것이 아니라, 수정 후 같은 URL의 첫 조회와 캐시된 조회를 비교한 결과입니다. 측정 환경의 왕복 지연은 약 80ms였습니다.

## 남은 한계와 확장 방향

- 캐시 대상이 늘어나면 **전체 삭제 대신 변경된 데이터와 관련된 항목만 무효화하도록 세분화**할 계획입니다.
- 현재 규모에서는 **별도 Redis보다 인메모리 캐시가 비용과 운영 복잡도 측면에서 적합하다고 판단**했습니다. 향후 여러 인스턴스를 상시 운영하게 되면 캐시 일관성을 위해 공유 캐시 도입을 다시 검토할 계획입니다.
