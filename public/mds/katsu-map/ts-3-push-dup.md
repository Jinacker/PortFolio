# 재설치 뒤 알림이 두 번 온 원인을 데이터 구조에서 해결했습니다

> 앱 재설치로 새 계정이 생기고 같은 푸시 토큰이 두 계정에 저장되는 과정을 확인한 뒤, 토큰 등록 시 기존 소유자를 정리하도록 바꾼 기록입니다.

## 한눈에

| | |
|---|---|
| **증상** | 앱을 재설치한 사용자의 한 기기에 같은 알림이 두 번 도착했습니다 |
| **원인** | 이전 계정이 남은 상태에서 같은 기기 토큰이 새 계정에도 저장됐습니다 |
| **해법** | 토큰 등록 시 다른 계정의 동일 토큰을 먼저 지우고 현재 계정에 저장했습니다 |
| **검증** | 삭제가 저장보다 먼저 실행되는 순서와 사용자당 세션 1개를 단위 테스트로 확인했습니다 |

## 재설치가 두 계정과 하나의 토큰을 만들었습니다

앱의 UUID는 기기 로컬 저장소에 있어 앱을 삭제하면 함께 사라집니다. 재설치 뒤에는 새 UUID와 새 계정이 생기지만, 이전 계정과 푸시 토큰은 서버 DB에 남아 있었습니다.

당시 DB 제약은 `(userId, token)` 조합만 중복을 막았습니다. 따라서 같은 기기의 토큰이 이전 계정과 새 계정에 각각 한 행씩 존재할 수 있었고, 전체 발송은 두 행을 모두 읽어 같은 기기에 두 번 전송했습니다.

```mermaid
flowchart LR
    A["앱 재설치<br/>로컬 UUID 소실"] --> B["새 UUID와 새 계정 생성"]
    B --> C["이전 계정의 토큰은 DB에 남음"]
    C --> D["같은 기기 토큰이<br/>두 계정에 저장"]
    D --> E["같은 알림 두 번 발송"]
```

## 세 가지 방법을 비교했습니다

| 후보 | 판단 |
|---|---|
| **토큰을 등록할 때 다른 계정의 동일 토큰 삭제** | 데이터 자체를 바로잡아 발송·알림 설정·대상 지정에 함께 적용되므로 **채택했습니다** |
| 발송할 때만 중복 토큰 제거 | 잘못된 데이터는 계속 남고 모든 발송 경로에 중복 제거 코드가 필요해 기각했습니다 |
| 기존 중복을 한 번에 정리 | 운영 데이터를 직접 바꾸는 작업이라 보류하고, 기기가 다시 등록될 때 정리되도록 했습니다 |

재설치해도 같은 계정을 찾는 방법도 검토했습니다. iOS Keychain과 달리 Android의 앱 저장 키는 앱 삭제와 함께 사라질 수 있어 공통 해결책으로 사용하지 않았고, 이후 카카오 계정 백업·복구로 보완했습니다.

## 삭제한 뒤 저장하는 순서를 보장했습니다

푸시 토큰 등록은 하나의 트랜잭션에서 **다른 계정이 가진 동일 토큰 삭제 → 현재 계정에 저장** 순서로 실행했습니다. 순서가 바뀌면 중복 제약에 걸릴 수 있어, 삭제가 저장보다 먼저 호출되는 것까지 테스트했습니다.

세션도 이전 세션 삭제와 새 세션 생성을 한 트랜잭션으로 묶었습니다. 중간에 실패해 세션이 하나도 남지 않는 상황을 막으면서 사용자당 세션을 하나로 유지했습니다. DB 스키마와 기존 API의 요청·응답 형식은 바꾸지 않았습니다.

## 확인된 결과와 남은 한계

- 단위 테스트에서 토큰 소유권을 옮기는 실행 순서와 사용자당 세션 1개를 확인했습니다.
- 실기기 재설치 뒤 알림이 한 번만 도착했다는 별도 측정 기록은 없어 결과를 수치로 단정하지 않았습니다.
- 기존 중복은 해당 기기가 토큰을 다시 등록할 때 정리되므로 즉시 반영되지 않습니다.
- 사용하지 않는 이전 계정 데이터와 푸시 수신 결과 추적은 아직 남아 있습니다.
