# 앱 전체가 느려졌다 — 인프라 탓부터 배제한 조사

> 특정 화면이 아니라 전반이 느려진 증상을, 가설을 하나씩 측정으로 배제하며 세 겹의 원인(쓰기 증폭·커넥션 1개·인덱스 누락)으로 좁힌 기록

## 한눈에

| | |
|---|---|
| **증상** | 홈·커뮤니티·기록·랭킹 — API가 겹치는 화면 전반이 느려짐. 목록 API 실측 0.7~1.0초 |
| **원인** | 인증마다 쌓이는 활동 기록 쓰기 증폭 + `connection_limit=1` + 인덱스 누락의 **복합** |
| **해법** | 매 요청 쓰기 제거(하루 1회로) + 무중단 인덱스 추가 + 커넥션 1→5 |
| **결과** | 3개월 뒤 로그 실측 p50 0.24초 · p95 0.51초 — 개선 상태 유지 확인 |

## 첫 번째 갈림길 — 서버가 느린가, 인프라가 느린가

전반적으로 느리면 보통 인프라(Cloud Run·네트워크)를 의심하게 된다. 그래서 가장 싼 실험부터 했다: **존재하지 않는 경로를 호출**했다.

인프라가 느리면 단순 404도 같이 느려야 한다. 빨랐다. 그럼 범인은 DB 쪽이다.

## 세 겹의 원인

| # | 발견 | 근거 |
|---|---|---|
| 1 | **쓰기 증폭** — 인증 요청마다 활동 기록 INSERT + 세션 UPDATE | 활동 기록 테이블 **89,390행** (유저 1,813명의 49배), 하루 최대 **15,663행** 증가. 탭 하나가 여러 API를 병렬 호출하니 탭 이동 한 번에 쓰기가 여러 건 |
| 2 | **`connection_limit=1`** | DB 연결 문자열 점검에서 발견 — 인스턴스당 커넥션 1개면 모든 쿼리가 한 줄로 선다 |
| 3 | **인덱스 누락** | 기록 수 표시 기능을 추가할 때 조회 컬럼의 인덱스를 빼먹은 것 확인 |

하나의 큰 원인이 아니라 작은 원인 셋의 곱이었다 — 쓰기가 몰리고, 그 쓰기가 커넥션 1개를 잡고, 읽기는 인덱스 없이 기다렸다.

## 고치다가 하나를 부쉈다 — 실패의 기록

1차 조치로 매 요청 활동 기록 쓰기를 제거했더니, 그 테이블을 세던 **관리자 DAU 통계가 유실**됐다. 하루 뒤 "KST 날짜가 바뀔 때 1회만 기록"하는 절충으로 보완했다.

> 최적화가 성능만 바꾸는 게 아니라 **지표의 의미**를 바꿀 수 있다 — "인증 호출 흔적"이던 DAU가 "하루 첫 방문"으로 재정의됐고, 이 변화를 위험으로 문서에 남겼다.

인덱스는 운영 테이블을 잠그지 않도록 `CREATE INDEX CONCURRENTLY`로 추가했다.

## 3개월 뒤의 사후 검증

당시 문서에는 개선 직후 수치가 없었다. 3개월 뒤 운영 로그를 백분위로 뽑아 빈칸을 채웠다.

| 시점 | 목록 API (/restaurants) |
|---|---|
| 조사 당시 (curl 실측) | 0.7 ~ 1.0초 |
| 3개월 뒤 (로그 백분위) | **p50 0.24초 · p95 0.51초** |

측정 방식이 다르므로(단발 curl vs 로그 백분위) 직접 비교에는 주의를 달았다 — 그래도 "개선이 유지되고 있다"는 결론에는 충분하다.

## 남은 한계

- 목록 API 응답 448KB는 미해결 — 페이로드 축소는 별도 과제로 남김
- `connection_limit=5`는 인스턴스당 값 — 스케일아웃 시 DB 총 커넥션 한도 재계산 필요
- 커넥션이 1로 세팅된 경위(환경 전환 시 설정 재검토 절차 부재)가 진짜 뿌리 — 프로세스 문제로 기록
