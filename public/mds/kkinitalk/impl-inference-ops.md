# 추론 서버 운영 설계 — 죽는 네 가지 방식을 막기

> AI 추론 서버는 일반 API 서버와 **고장 나는 방식이 다릅니다.** 요청당 수 GB 메모리, 수십 초의
> 모델 로딩, 동기 블로킹 추론. 일반 웹 서버처럼 짜면 **"느린 것"이 "죽은 것"으로 오판**되어
> 인스턴스가 재시작되는 최악의 루프에 빠집니다.

## 네 가지 고장 방식

| | 무엇이 문제인가 |
|---|---|
| ① 콜드스타트 | SAM 체크포인트 약 2.4GB, 로드에 수십 초 — 그동안 들어온 트래픽은 전부 실패하거나 무한 대기 |
| ② GPU 메모리 | 동시 요청 수 = 동시 추론 수가 되면 2~3건만으로 CUDA OOM — 진행 중인 요청이 전부 함께 죽음 |
| ③ 이벤트 루프 | `async def` 안에서 동기 추론(torch)을 부르면 수 초간 루프 전체가 멈춤 — `/health`조차 응답 불가 |
| ④ 타임아웃 | 하나만 두면 어디가 느린지 구분 불가, 없으면 느린 자원 하나가 세마포어를 무한 점유 |

## 해결

**콜드스타트** — `/health`(프로세스 생존)와 `/ready`(모델 로드 완료)를 분리했습니다.
로드 중에는 `/ready`가 503을 반환해 트래픽을 차단하고, 로드 직후 더미 이미지로 **워밍업 추론**까지
돌려 첫 사용자가 첫 추론의 지연을 겪지 않게 했습니다.

**GPU 동시성** — 외부 큐(Celery/Redis)는 무상태 원칙과 충돌하고 MVP에 과합니다.
`asyncio.Semaphore`로 프로세스 내에서 제한하되, **mock·gemini 백엔드도 같은 경로를 지나게**
했습니다 — 경로를 분리하면 로컬에서 한 번도 검증되지 않는 코드 경로가 생기기 때문입니다.
멀티워커 함정(워커마다 모델 로드 → GPU 메모리 N배)은 Dockerfile에 단일 워커를 박아 막았습니다.

**타임아웃 — 계층별 3개, 상태코드도 구분**

| 계층 | 값 | 초과 시 |
|---|---|---|
| 이미지 다운로드 | 10s | **502** — 원인은 업스트림, 재시도 의미 있음 |
| LLM/Vision 호출 | 30s | **502** |
| 분석 전체 (세마포어 대기 포함) | 60s | **504** — 이 서버의 처리 능력 초과 |

바깥(60s)이 안쪽의 합(10+30)보다 커야 하위 타임아웃이 의미를 갖고, 전체 타임아웃이
**세마포어 대기까지 포함**해야 폭주 시 무한 대기가 아니라 명시적 504로 끝납니다.

## 결과

- 고려사항 15개 × 해결 장치 × 잠그는 테스트를 표로 대응 — "위험을 한 곳에 응집시키고 그 지점을 테스트로 잠근다"
- 세마포어 경로가 mock 테스트에서 **상시 통과** (경로 단일화 덕분)
- 응답에 `processingMs`를 실어 "느려졌다"를 숫자로 말할 수 있게 함
- 참조 데이터 로드 실패 시 **기동 자체가 실패**(fail-fast) — 데이터 없이 뜬 서버가 조용히 틀린 답을 내지 않게
- 이 장치들은 나중에 부하·동시성 검증에서 실측으로 증명했습니다 (AI 검증 · 부하 문서 참고)

## 배운 점

- 추론 서버는 **"느린 것"과 "죽은 것"을 구분할 수 있게** 만들어야 한다 — `/ready` 분리와 타임아웃 계층이 전부 그 목적
- 안전장치는 **모든 경로가 지나게** 만들어야 검증된다 — GPU 전용 경로에만 뒀다면 로컬에서 한 번도 안 밟혔을 것
- 상태코드가 **소비자의 다음 행동을 결정한다** — 502(재시도)와 504(과부하)를 구분해야 백엔드가 올바르게 대응한다
