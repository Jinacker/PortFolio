# AI 에이전트로 개발하면서 생긴 검증 공백

> AI가 쓴 코드는 빠르지만, 무엇을 검증할지는 여전히 사람이 정한다

## 문제 상황

이 프로젝트는 **AI 에이전트(Claude Code) 기반으로 개발**했다.
하네스(권한 deny 목록, 저장소별 규칙 문서, 서브에이전트 분업)를 걸어 두고 작업했다.

속도는 확실히 빨랐다. 그런데 **두 번의 사고가 같은 모양**으로 났다.

| | 자동 지표 | 실제 |
|---|---|---|
| 가짜 챗봇 (트러블슈팅 7) | 200 · 에러 0 · 테스트 366 통과 | 사용자에게 가짜 응답이 나갔다 |
| 응급 가드 (트러블슈팅 5) | 단위 테스트 11개 통과 · **라인 커버리지 100%** | 주 입력 경로에서 3/4 누락 |

**둘 다 초록불이었고, 둘 다 사용자의 "실제로 써 봐"에서 드러났다.**

## 원인 분석 — 검증 계층에 두 줄이 빠져 있었다

기존 계층은 전부 **"코드가 맞는가"** 를 묻고 있었다.
여기에 **L0 환경 동등성**("검증한 환경이 배포된 환경인가")과
**L0.5 경로 동등성**("검증에 넣은 입력을 사용자도 그렇게 만드는가")을 추가했다.
계층 구성과 각 층이 못 잡는 것의 대응표는 탭 2 · 검증 5에 있다.

## AI 에이전트 개발에서 특히 생기는 것

이 두 공백은 AI 개발이 아니어도 생긴다. 다만 **AI 개발에서 더 잘 생긴다**고 느꼈다.

1. **속도가 빨라 "왜 이렇게 했지"를 되묻는 지점이 줄어든다.**
   코드가 빨리 나오니 초록불이 뜨면 그대로 넘어간다
2. **테스트도 함께 생성되니 "이 테스트가 무엇을 못 잡는가"를 안 묻게 된다.**
   응급 가드 테스트 11개가 딱 그랬다 — `escalate`만 단언하고 있었다
3. **고치는 김에 눈에 띈 것까지 고치면 검증한 변경과 검증 안 한 변경이 한 커밋에 섞인다.**
   실제로 내 수정 두 건이 각각 다음 버그를 만들었다
   - 무한 반복 버그 → `useFocusEffect` deps에 상태를 넣어 에러를 스스로 삼킴
   - "음성 파일이 없습니다" → 포맷을 고치면서 **주석이 틀렸던 헤더 설정까지** 함께 지움

## 선택지 비교 — 무엇으로 막을 것인가

| 후보 | 문제 |
|---|---|
| 테스트를 더 많이 쓴다 | **커버리지 100%에서 뚫렸다.** 양의 문제가 아니었다 |
| 코드 리뷰를 강화한다 | 리뷰도 "코드가 맞는가"를 본다. 경로·환경 동등성은 리뷰로 안 보인다 |
| **배포된 것을 직접 찌르는 스크립트를 만든다** | 유지 비용이 들지만, 이 종류의 결함은 **이것으로만 보인다** |

세 번째를 택했다. 손으로 `curl` 하면 **다음 배포 때는 안 하게 된다.**

## 결과 — 측정으로 검증

배포 후 재검증을 **한 명령으로 고정**했다.

```
$ API_BASE_URL=https://.../api/v1 npm run verify:chatbot-live

1. 상담이 시작되는가 (가짜 어댑터면 운영에서 503)     ✅
2. 응급 신호 — 배포된 가드가 고쳐진 가드인가          ✅ 4/4
3. 오탐 — 격상되면 안 되는 것                        ✅ 2/2
4. 무응답 종결 — 빈 입력 3회에 종결                   ✅
```

| 검사 | 무엇을 잡는가 |
|---|---|
| 상담 시작 | 가짜 어댑터가 운영에 나가고 있지 않은가 (트러블슈팅 7) |
| 응급 4건 | **배포된 가드가 고쳐진 가드인가** (L0) |
| 오탐 2건 | 넓힌 어휘가 일상 발화까지 격상시키지 않는가 |
| 무응답 종결 | 벤더가 종결 횟수를 바꾸면 앱 타이머가 어긋난다 |

**입력이 음성 파일이 아니라 문자열인 것은 의도적이다.**
이 스크립트가 묻는 것은 *"배포된 코드가 맞는 코드인가"* 하나이고, 그러려면 입력이 고정돼야 한다.
STT를 끼우면 실패했을 때 **가드가 틀린 건지 STT가 다르게 들은 건지 구분되지 않는다.**
대신 넣는 문자열이 **STT가 실제로 돌려줬던 것**이라 음성 경로의 실패 모드는 보존된다.

그리고 **배포 지연을 "배포 안 됨"으로 읽지 않도록** 절차를 문서화했다.
push 후 반영까지 25~35분 걸리는데, 15분 만에 확인하고 "안 붙었다"고 잘못 보고한 적이 있다.
`/health`의 `uptimeSeconds`가 **작아졌으면** 재기동된 것이다.

## 남은 한계

- L0.5를 계층으로 정의했지만 **다른 순수 함수들에 같은 검사를 적용하지 않았다.**
  응급 가드에서만 밟았다
- 검증 스크립트가 **CI에 연결돼 있지 않다.** 사람이 배포 후 돌려야 한다
- AI 서버 쪽에는 아직 **L0에 해당하는 배포 후 검증이 없다**

## 배운 점

- **AI 시대에 병목은 코드 작성이 아니라 "무엇을 검증할지 정하는 일"이라는 것.**
  이 프로젝트에서 오래 걸린 것은 전부 판단이었지 타이핑이 아니었다
- **자동 검증은 내가 상상한 경로만 검증한다는 것.**
  상상하지 못한 경로는 커버리지 숫자에 나타나지도 않는다
- **한 커밋에 검증한 변경과 검증 안 한 변경을 섞지 않는다는 것.**
  내 수정 두 건이 각각 다음 버그를 만들고 나서 배웠다
