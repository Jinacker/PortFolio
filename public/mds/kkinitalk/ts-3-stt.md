# 벤더 STT가 음성을 못 읽는다 — 두 번의 실험으로 원인 좁히기

> "음성만 503"에서 컨테이너 포맷까지 좁혀 들어간 진단 과정

## 무슨 문제가 있었나

- 챗봇 텍스트 대화는 정상인데 **"눌러서 말하기"만 실패** — 사용자에게는 "지금은 대화할 수 없어요"만 표시
- 로그엔 벤더의 불투명한 `503 ENGINE_UNAVAILABLE`뿐 — **우리 잘못인지 벤더 장애인지도 구분 불가**

## 원인을 어떻게 찾았나 — 변수를 하나씩만 바꾸는 실험

| 실험 | 결과 |
|---|---|
| ① 우리 서버를 빼고 벤더 직접 호출 (WAV) | 200 — 벤더는 살아 있다. **우리가 보내는 것이 문제** |
| ② 같은 WAV 바이트를 `audio/m4a` **라벨**로 전송 | 200 — MIME 라벨은 안 본다 |
| ② 진짜 m4a(AAC) **컨테이너** 전송 | 503 — **컨테이너 자체를 못 읽는 것** 확정 |

- 근본 원인은 문서 — 벤더 문서에 STT 지원 포맷이 없었고, 앱 녹음 프리셋은 전부 m4a
- 라벨만 고쳤다면 소용없었을 것 — **실험이 헛수고를 막았다**

## 어떤 선택지가 있었고, 무엇을 선택했나

### 서버에서 변환 vs 앱이 처음부터 WAV 녹음

- 서버 ffmpeg 변환은 **업로드된 음성이 서버 디스크에 남는다** — 민감정보 체류
- 앱이 16kHz mono WAV로 녹음하는 쪽 채택 — 음성 인식엔 16kHz면 충분하고, 44.1kHz 스테레오는 파일이 5~6배 커져 **어르신 기기의 업로드가 곧 대기 시간**

### 그런데 이 결정은 안드로이드에서 틀렸다

- "안드로이드 실기기 미검증"을 **한계로 적어 두고 확인하지 않았다**
- 안드로이드는 WAV 녹음을 미지원 — 라벨만 `wav`인 파일이 올라가 **안드로이드 음성 대화는 항상 실패 중**이었다
- 최종 해법(매직 바이트로 컨테이너 판별 + `stdin→stdout` 파이프 변환, 디스크에 안 남음)은 **팀원이 구현** — 내 몫은 컨테이너 문제까지의 진단
- 내가 반대한 이유(민감정보 체류)는 파이프 방식으로 해소 가능했다 — **반대 이유가 다른 방법으로 해소되는지 먼저 찾았어야 했다**

## 결과 — 측정으로 검증

- 실제 한국어 WAV로 STT 200 OK, 3.3초
- 서버 실패 메시지를 **원인별 3종으로 분기** — audio 필드 없음 / 0바이트 녹음 / 크기 초과
- 앱에서 업로드 전 크기 확인 — 1KB 미만(무음)은 벤더를 호출하지 않음
- 벤더 요청 항목에 "STT 지원 포맷 문서화" 등록

## 경험을 통해 배운 점

- 에러가 원인을 구분해 주지 않으면 **실험으로 구분한다**는 것 — "우리인가 벤더인가" → "라벨인가 컨테이너인가"
- **같은 바이트를 다른 라벨로 보내는 것**처럼, 변수를 하나만 바꾸는 실험 설계가 핵심이라는 것
- **한계를 적는 것과 확인하는 것은 다르다**는 것 — 적기만 하면 그건 인계이지 해결이 아니다
