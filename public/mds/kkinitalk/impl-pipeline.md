# 식단 분석 파이프라인 — 모델을 갈아끼워도 살아남는 구조

> 이 서비스의 심장은 **식사 사진 → 영양소**입니다. 그런데 시작 시점에 어떤 모델을 쓸지 확정할 수
> 없었습니다 — 자체 모델(SAM + Food-101)은 GPU 인스턴스가 없었고, 상용 Vision API는 비용을 몰랐습니다.
> 그래서 **모델이 바뀌어도 파이프라인이 살아남는 구조**를 먼저 만들었습니다.

## 문제

인식 방식마다 출력 형태가 다릅니다.

- **SAM + Food-101** — 세그멘테이션(픽셀 마스크)과 분류(라벨)가 2단계로 분리
- **GPT Vision / Gemini** — 한 번의 호출로 음식명과 면적 비중을 함께 반환

이 둘을 같은 코드가 소비하게 만들지 않으면, 모델을 바꿀 때마다 영양 계산 로직까지 다시 써야 합니다.

## 설계 — 교체 대상을 먼저 못박는다

```
① 세그멘테이션: 음식별 영역 + 면적          [불변]
② 크롭 → 분류: 메뉴명 + confidence          [교체 대상]
③ 영양 테이블 매칭: 메뉴명 → 1인분 영양소    [교체 대상]
④ 면적 비중 → 양 배율 → 스케일               [불변]
```

인식(①②)을 `FoodAnalyzer` 인터페이스 뒤로 숨기고, 계약을
`RecognizedRegion(label, confidence, area_share)` 하나로 고정했습니다.

핵심은 **면적을 픽셀이 아니라 비중(area_share)으로 계약**한 것 — SAM은 픽셀 마스크를 주고
GPT는 "상 전체의 몇 %"를 줍니다. 픽셀로 계약하면 GPT 백엔드가 계약을 못 지킵니다.
**비중은 양쪽 다 표현 가능한 최소공배수**이고, 배율 계산도 해상도와 무관해집니다.

## 양(portion)을 어떻게 정할 것인가

사진만으로 "얼마나 먹었는지"는 알 수 없습니다. 저울도 깊이 센서도 없습니다.

| 후보 | 문제 |
|---|---|
| 사용자가 조금/보통/많이 선택 | **어르신 조작을 늘린다** — 프로젝트 대전제와 충돌 |
| 절대 부피 추정 | 단일 카메라로는 깊이 정보가 없어 신뢰 불가 |
| **상차림 내 상대 면적으로 추정** | 절대량은 못 구하지만 "평소보다 많이/적게"는 잡힌다 |

음식마다 통상 면적 비중을 테이블에 두고, 실제 비중과의 비율로
**small(×0.65) / regular(×1.0) / large(×1.35)** 를 판정합니다.
절대 정확도가 아니라 **매일 먹는 양의 변화를 추세로 보는 것**이 목표라는 트레이드오프를
명시적으로 수용한 설계입니다.

## 배운 점

- **인터페이스 계약을 어느 수준으로 잡느냐가 교체 가능성을 결정한다** — 픽셀로 계약했다면 GPT를 못 붙였다
- 못 하는 것을 인정하고 **목적에 맞는 근사**를 고르는 게 나을 때가 있다 —
  절대 그램 수를 포기했더니 사용자 조작이 0이 됐다
- **가짜(mock) 구현에도 설계가 필요하다** — 고정값을 아무렇게나 뒀으면 배율 분기를 키 없이 검증할 수 없었다
