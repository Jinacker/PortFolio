# 부하·동시성 검증 — 코드에만 있던 안전장치를 증명

> 추론 서버 운영 설계에서 세마포어·타임아웃·executor 오프로드를 넣어 뒀는데 —
> **전부 한 번도 밟아 본 적이 없었습니다.** "코드에 있다"와 "동작한다"는 다릅니다.

## 왜 실 GPT가 아니라 mock인가

| 후보 | 문제 |
|---|---|
| 실 GPT로 동시 요청 | 응답이 2~13초로 흔들려 **세마포어 때문에 밀린 건지 API가 느린 건지 구분 불가** |
| **mock에 고정 지연 주입** | 큐잉이 **산술로 드러난다** — 지연 1초·6건·동시성 1이면 6초, 3이면 2초여야 한다 |

**결정론이 목적이지 비용 절약이 아닙니다.** 비용 0원은 부수 효과입니다.
타임아웃도 값을 낮춰(60초 → 2초) 메커니즘을 재고, **운영 기본값이 60초인지는 별도 시나리오로
단언**했습니다 — 안 그러면 "60초를 쟀다"로 읽힙니다.

## 첫 실행이 전부 422로 죽었다

```
concurrency=1  총 0.06초 (기대 ≈6초)  200 0/6
  단건: 422 FORBIDDEN_IMAGE_HOST
```

**SSRF 방어가 로컬 이미지 서버(127.0.0.1)를 차단**한 것 — 부하 테스트를 막았지만, 동시에
방어가 실제로 동작한다는 우연한 증거였습니다. 테스트용으로 문을 열 때도 자물쇠를 둘로 걸었습니다 —
예외 플래그와 허용 호스트 목록을 **동시에** 요구해, 하나만 실수로 켜져도 열리지 않는 구조입니다
(운영 가짜 AI 사고의 교훈을 새 위험 설정에 바로 적용한 것).

## 결과

| 검증 | 결과 |
|---|---|
| 세마포어 큐잉 (지연 1s × 6건) | 동시성 1 → **6.15초** / 동시성 3 → **2.09초** — 산술 그대로, 실제로 직렬화됨 |
| 전체 타임아웃 | 동시 3건·지연 1.5s·타임아웃 2s → `[200, 504, 504]` — **대기 중인 요청도 명시적 504로 종료** |
| 다운로드 타임아웃 | 느린 호스트(3s) + 타임아웃 1s → **502** at 1.04초 (사설 IP 차단 422와 구분) |
| 운영 기본값 | `60.0 > 10.0 + 30.0` — 바깥 타임아웃 > 안쪽 합을 시나리오로 단언 |

**가장 중요한 결과 — 이벤트 루프.** mock 지연을 비블로킹(`asyncio.sleep`)과
블로킹(`time.sleep`)으로 대조했습니다. 블로킹 쪽은 동기 추론을 executor 없이 부르면
정확히 그렇게 되는 **대조군**입니다.

| | `/health` 폴링 횟수 | p50 | 최악 |
|---|---|---|---|
| 비블로킹 (현재 코드) | **85회** | **3ms** | 17ms |
| 블로킹 (대조군) | **4회** | **1,474ms** | 1,549ms |

같은 시간 동안 헬스체크를 4번밖에 못 찍었다는 것 자체가 증거입니다 — **이벤트 루프가 멈춰 폴링조차
못 했고, 정확히 추론 시간만큼 막혔습니다.** 로드밸런서 헬스체크 타임아웃(보통 1~5초)을 생각하면
이 상태에서는 추론이 도는 동안 인스턴스가 비정상 판정되어 제거됩니다.

`pytest 105 passed` · 실 API 호출 0회 · 비용 0원.

## 배운 점

- **"코드에 있다"와 "동작한다"는 다르다** — 전부 있었지만 어느 것도 밟아 본 적이 없었다
- **대조군이 있어야 증명이 된다** — 비블로킹만 재면 "17ms 나왔다"지만, 나란히 놓으면
  "막히는 코드였다면 1,549ms였다"가 된다
- **측정하려다 다른 방어를 밟는 것 자체가 검증이다** — 422로 죽은 첫 실행이 SSRF의 첫 실서버 확인이었다
- 위험한 문을 열 때는 **자물쇠를 둘로** — 하나만 실수로 풀려도 안 열리게
