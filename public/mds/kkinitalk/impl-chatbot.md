# 외부 챗봇 연동 — 남이 만든 AI를 우리 얼굴로 내보내기

> 어르신 건강 상태 수집은 설문이 아니라 **음성 대화**여야 합니다. 벤더의 건강상담 챗 엔진
> (상담 LLM · STT · TTS)을 연동했는데 — **우리 서비스의 얼굴로 나가지만 우리가 만들지 않은 AI**를
> 붙이는 일이었습니다.

## 문서를 그대로 믿지 않았다

API 가이드를 읽고 바로 구현하지 않고 **먼저 실제 API를 찔러 봤습니다.** 어긋나는 지점이 나왔습니다.

- STT 지원 포맷이 문서에 없음 — 모바일 기본 포맷(m4a)이 실제로는 안 됨
- 무응답 종결 횟수가 다름 — 문서는 "30초×2회", 실측은 빈 입력 3회째 종결
- 에러 응답 포맷이 세 가지로 갈림

구현 전 실측으로 **문서 모순 3건 해소, 미문서화 동작 2건 발견** — 찔러 보기 전에 코드를 썼다면
이 모순들이 그대로 구현에 녹았을 것입니다.

## 앱이 직접 붙는가, 서버가 중계하는가

| 후보 | 문제 |
|---|---|
| 앱 → 벤더 직접 | **전 사용자가 공유하는 벤더 토큰이 앱에 내려간다** — APK를 뜯으면 추출되고, 유출돼도 앱 업데이트 없이 회수 불가 |
| **백엔드가 중계** | 왕복 1회 증가 — 대신 토큰이 서버에만 존재 |

중계를 택하자 부가 효과가 컸습니다 — 벤더의 에러 3포맷을 우리 1포맷으로 정규화하고,
응급 안내를 얹고, 토큰 한도를 서버에서 관측할 수 있게 됐습니다.

특히 **401을 그대로 내리지 않습니다.** 벤더 토큰 만료는 우리 쪽 문제인데, 앱 인터셉터가
401을 받으면 **어르신을 로그아웃시킵니다.** 503으로 접었습니다.

## AI가 만든 건강정보를 어디에 저장하는가

챗봇이 "어르신이 당뇨가 있다고 말했다"고 판단하면 그게 곧바로 식단 판정에 반영되어야 할까요?
**반영되면 안 됩니다.** LLM의 오인식이 곧바로 식사 추천을 바꾸게 되기 때문입니다.

챗봇 결과는 스냅샷 테이블에 **격리**하고, 보호자 승인 후에만 도메인 진실에 반영되게 했습니다.
**AI 출력과 도메인 진실을 물리적으로 분리하고 그 사이에 사람을 둔 것** — 반영이 늦어지는
트레이드오프를 감수하고 의도적으로 안전한 쪽에 멈춰 둔 설계입니다.

## 결과

- 벤더 에러 3포맷 → 1포맷 정규화, 401 → 503 변환으로 어르신 로그아웃 방지
- 어댑터에 **부팅 자가진단** — 기동 시 토큰으로 연결 가능 여부를 로그로.
  첫 사용자 요청이 아니라 부팅 시점에 알아야 합니다
- 동의를 가입 트랜잭션에 포함 — "계정은 있는데 동의 기록이 없는" 사용자가 생기지 않게
- 실서버 왕복 실측 — 상담 응답 1.3~1.9초, STT 3.3초
- Jest 377 passed (챗봇 41개 포함)

## 배운 점

- **문서는 가설이고 실측이 사실이다** — 붙이기 전에 찔러 본다
- 외부 AI는 **경계에서 격리한다** — 에러 포맷·토큰·출력 신뢰도 전부 경계에서 정규화된다
- AI 출력과 도메인 진실 사이에 **사람을 두는 것은 미완성이 아니라 설계다**
