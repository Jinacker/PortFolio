# 부하 테스트로 AI 서버의 동시 실행 제한과 타임아웃을 검증했습니다

> 코드에 추가해 둔 동시 실행 제한·타임아웃·비동기 처리가 실제 요청에서도 동작하는지, 고정 지연을 넣은 재현 가능한 시나리오로 확인했습니다.

## 한눈에

| | |
|---|---|
| **위험** | 무거운 분석 요청이 동시에 들어오면 메모리 사용량과 대기 시간이 함께 늘어날 수 있었습니다. |
| **안전장치** | 분석 동시 실행 수, 전체 처리 시간, 이미지 다운로드 시간을 각각 제한했습니다. |
| **검증 방법** | 외부 AI 대신 고정 지연을 반환하는 분석기를 사용해 예상 대기 시간을 먼저 계산했습니다. |
| **결과** | 동시 실행 수에 따른 처리 시간, 대기 시간을 포함한 타임아웃, 분석 중 헬스체크 응답을 확인했습니다. |

## 서버가 오래 점유되는 네 가지 경로를 나눴습니다

AI 분석 서버는 일반 API보다 한 요청의 처리 시간이 길고, 로컬 모델을 사용하면 CPU·GPU도 함께 점유합니다. 그래서 장애가 생길 수 있는 경로와 제한 장치를 먼저 짝지었습니다.

| 발생할 수 있는 상황 | 적용한 방식 |
|---|---|
| 모델이 아직 준비되지 않음 | `/health`와 `/ready`를 나눠 준비 전에는 분석 트래픽을 받지 않습니다. |
| 분석 요청이 한꺼번에 실행됨 | 분석 동시 실행 수를 세마포어로 제한합니다. |
| 동기 추론이 다른 요청까지 막음 | 모델 로드와 추론을 별도 실행 흐름에서 처리합니다. |
| 외부 호출이나 대기가 끝나지 않음 | 전체 60초·이미지 다운로드 10초·외부 AI 호출 30초의 상한을 둡니다. |

코드에 제한이 존재하는지만 확인하지 않고, 실제 HTTP 요청에서 대기와 종료 시점이 기대한 대로 나타나는지 측정했습니다.

## 외부 AI 대신 고정 지연을 넣었습니다

실제 AI API는 호출마다 2~13초로 시간이 달라 원인을 구분하기 어렵고 비용도 발생합니다. 검증에서는 분석기가 정확히 1초 뒤 응답하도록 설정했습니다.

동시에 6건을 보낼 때 실행 제한이 1이면 약 6초, 3이면 약 2초가 걸려야 합니다. **측정 전에 예상값을 먼저 정하고**, 결과가 그 관계를 따르는지 확인했습니다.

![동시 실행 제한에 따른 대기 시간 실측](/assets/experiences/kkinitalk/capture-semaphore-math.svg)

| 조건 | 예상 | 실제 |
|---|---:|---:|
| 지연 1초 · 동시 6건 · 실행 제한 1 | 약 6초 | **6.15초** |
| 지연 1초 · 동시 6건 · 실행 제한 3 | 약 2초 | **2.09초** |

실행 제한이 요청을 누락시키는 것이 아니라, 정해진 수만 실행하고 나머지를 기다리게 한다는 것을 확인했습니다.

## 대기 시간도 전체 제한 시간에 포함했습니다

운영의 60초를 그대로 기다리지 않고 테스트에서 전체 제한 시간을 2초로 낮춰 같은 동작을 확인했습니다.

| 시나리오 | 결과 |
|---|---|
| 처리 지연 4초 · 전체 제한 2초 | **2.01초에 `504 INFERENCE_TIMEOUT`** |
| 동시 3건 · 처리 1.5초 · 실행 제한 1 · 전체 제한 2초 | `[200, 504, 504]` |
| 이미지 응답 지연 3초 · 다운로드 제한 1초 | **1.04초에 `502 IMAGE_FETCH_FAILED`** |

두 번째 시나리오에서는 실제 분석 시간이 1.5초여도 앞 요청을 기다린 두 건이 2초를 넘겨 종료됐습니다. 큐에서 기다리는 시간을 제외하면 사용자가 체감하는 전체 대기 시간이 제한을 넘어갈 수 있으므로, **대기부터 응답까지를 하나의 상한으로 처리**했습니다.

## 분석 중에도 헬스체크가 응답하는지 비교했습니다

동기 추론이 이벤트 처리 흐름을 막으면 분석과 관계없는 헬스체크까지 늦어집니다. 현재의 비동기 처리와 일부러 막히게 만든 비교용 구현을 같은 조건에서 측정했습니다.

![분석 중 헬스체크 응답 비교](/assets/experiences/kkinitalk/capture-eventloop.svg)

| 처리 방식 | 헬스체크 응답 횟수 | p50 | p95 | 가장 느린 응답 |
|---|---:|---:|---:|---:|
| 비동기 처리 | **85회** | 3ms | 5ms | 17ms |
| 일부러 막히게 만든 비교 구현 | **4회** | 1,474ms | 1,549ms | 1,549ms |

분석이 진행되는 동안에도 현재 구현의 헬스체크는 계속 응답했습니다. 반대로 동기 대기 상태에서는 분석 지연과 비슷한 시간만큼 헬스체크도 함께 막혔습니다.

## 검증 범위와 남은 과제

- 이 결과는 고정 지연을 주는 mock 분석기로 측정했습니다. 실제 GPU 메모리 경합과 모델 처리량은 재현하지 못했습니다.
- 동시 실행 수는 제한하지만 대기열 길이 자체에는 상한이 없습니다. 요청이 크게 몰릴 때는 대기열 제한이나 조기 거절 정책이 필요합니다.
- 세마포어는 서버 프로세스 안에서만 동작합니다. 인스턴스가 늘어나면 전체 동시 분석 수는 인스턴스 수만큼 함께 늘어납니다.
- 운영 기본값 60초는 테스트에서 그대로 기다리지 않고 설정값과 제한 시간의 관계만 확인했습니다.
