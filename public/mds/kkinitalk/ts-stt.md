# 벤더 STT가 음성을 못 읽는다 — 두 번의 실험으로 원인 좁히기

> 챗봇 텍스트 대화는 정상인데 **"눌러서 말하기"만 실패**했습니다. 로그엔 벤더의 불투명한
> `503 ENGINE_UNAVAILABLE`뿐 — 우리가 잘못 보낸 건지, 벤더 엔진이 죽은 건지도 구분되지 않았습니다.

## 가설을 하나씩 잘라내는 실험

추측으로 코드를 고치지 않고, **변수를 하나만 바꾸는 실험 두 번**으로 원인을 좁혔습니다.

**실험 ① — 우리 문제인가, 벤더 문제인가**
우리 서버를 빼고 벤더 API를 직접 호출 → WAV 파일로 200 OK.
벤더 엔진은 살아 있고, **우리가 보내는 것에 문제가 있습니다.**

**실험 ② — MIME 라벨 문제인가, 컨테이너 문제인가**

| 보낸 것 | 결과 |
|---|---|
| WAV(LinearPCM) + `audio/wav` | 200 |
| **같은 WAV 바이트** + `audio/m4a` 라벨 | **200 — MIME 라벨은 안 본다** |
| 진짜 m4a(AAC) 컨테이너 | **503 — 컨테이너 자체를 못 읽는 것** |

라벨을 고쳐도 소용없었을 것임이 확정됐습니다. 근본 원인은 벤더 문서에 **STT 지원 포맷이 명시돼
있지 않았고**, 앱 녹음 프리셋이 전부 m4a였다는 것 — 그대로 붙이면 음성이 통째로 안 됩니다.

## 선택 — 그리고 그 선택이 틀렸다

서버에서 ffmpeg 변환(음성이 서버 디스크에 남음 — 민감정보) 대신 **앱이 처음부터
16kHz mono WAV로 녹음**하는 쪽을 택했습니다. 음성 인식엔 16kHz면 충분하고, 44.1kHz 스테레오는
파일이 5~6배 커져 **어르신 기기의 업로드가 곧 대기 시간**이 되기 때문입니다.

**이 결정은 안드로이드에서 틀렸습니다.** "안드로이드 실기기 미검증"을 한계로 적어 두고
확인하지 않았는데 — 안드로이드는 WAV 녹음을 지원하지 않아, 라벨만 `wav`인 AMR/3GP 바이트가
올라가고 있었고 **안드로이드 음성 대화는 항상 실패하고 있었습니다.**

최종 해법(서버가 **매직 바이트로 컨테이너를 판별**해 필요 시에만 변환, `stdin→stdout` 파이프라
디스크에 안 남음)은 **팀원이 만들었습니다.** 제 몫은 컨테이너 문제까지의 진단이었고,
제가 서버 변환을 반대한 이유(민감정보 체류)는 파이프 방식으로 해소됐습니다 —
**반대 이유가 다른 방법으로 해소될 수 있는지 먼저 찾았어야 했습니다.**

## 결과

- 실제 한국어 WAV로 STT 200 OK, 3.3초
- 서버 실패 메시지를 **원인별 3종으로 분기** — "audio 필드 없음 / 0바이트 녹음 / 크기 초과".
  같은 메시지에 원인이 여러 개면 다음 사람이 같은 디버깅 시간을 씁니다
- 앱에서 업로드 전 크기 확인 — 1KB 미만(WAV 헤더뿐인 무음)은 벤더를 호출하지 않음
- 벤더 요청 항목에 "STT 지원 포맷 문서화" 등록

## 배운 점

- 에러가 원인을 구분해 주지 않으면 **실험으로 구분한다** — "우리인가 벤더인가" → "라벨인가
  컨테이너인가", 두 번의 이분법
- **같은 바이트를 다른 라벨로 보내는 것**처럼, 변수를 하나만 바꾸는 실험 설계가 핵심
- **한계를 적는 것과 확인하는 것은 다르다** — 적기만 하면 그건 인계이지 해결이 아니다
