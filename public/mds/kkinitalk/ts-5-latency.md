# 추천·복약 안내의 출력 범위를 줄여 GPT 응답 시간을 단축했습니다

> 사용자에게 필요한 정보만 생성하도록 프롬프트와 출력 상한을 정리한 뒤, 같은 입력을 GPT-4o-mini에 변경 전·후 각각 3회씩 호출해 응답 시간과 출력 토큰을 비교했습니다.

## 한눈에

| | |
|---|---|
| **증상** | 다음 끼니 추천과 복약 주의 문구를 기다리는 시간이 길었습니다. |
| **관찰** | 추천은 여러 메뉴와 일반적인 인사말까지, 복약 안내는 약별 설명과 전체 안내를 함께 생성하고 있었습니다. |
| **수정** | 추천은 음식 1개와 2문장 이내의 안내로, 복약 주의는 약마다 필요한 한 문장으로 제한했습니다. 예상 밖의 장문에는 700토큰의 안전 상한을 뒀습니다. |
| **결과** | 3회 호출의 중앙값에서 추천은 **4.51초 → 1.75초**, 복약 주의는 **2.67초 → 1.87초**로 줄었습니다. |

## 사용자에게 보여줄 결과보다 길게 생성하고 있었습니다

기존 프롬프트는 추천 메뉴를 2~3개 만들고 일반적인 건강 인사까지 덧붙이도록 했습니다. 복약 안내도 약마다 최대 2문장의 설명을 만들고, 같은 내용을 아우르는 전체 안내 문구를 다시 생성했습니다.

### 실제 추천 응답 예시

| **변경 전** | **변경 후** |
|---|---|
| `구운 닭가슴살 샐러드`·`두부 스테이크와 채소 볶음`·`야채죽`을 추천한 뒤, “어르신, 오늘 저녁은 건강하고 맛있는 식사로 준비해 보세요. 항상 건강에 유의하시길 바랍니다.”라는 일반적인 안내를 덧붙였습니다. | 음식 하나를 고르고, “오늘은 단백질이 부족하고 나트륨은 조금 많았어요. 다음 끼니엔 닭가슴살 구이를 추천드려요.”처럼 **현재 상태와 다음 행동만 전달**했습니다. |
| **3회 중앙값: 출력 119토큰 · 4.51초** | **3회 중앙값: 출력 72토큰 · 1.75초** |

## 출력 범위를 줄이고 예외적인 장문에는 상한을 뒀습니다

| 방법 | 판단 |
|---|---|
| **답변 길이·순서 제한** | 필요한 출력 자체를 줄이기 위해 적용했습니다. |
| **최대 700토큰** | 예외적인 장문을 막는 안전 상한으로 적용했습니다. |
| HTTP 클라이언트 재사용 | 우선순위를 낮췄습니다. |
| 모델 교체 | 기존 모델에서 먼저 개선했습니다. |

추천 문구는 `부족하거나 많은 영양소 설명 → 다음 끼니 음식 제안` 순서로 끝내도록 했습니다. 복약 주의도 전체 안내를 반복하지 않고 약마다 필요한 주의사항만 구조화해 반환하도록 바꿨습니다.

### 실제 적용한 프롬프트와 설정

```text
# app/services/prompts.py

[다음 끼니 추천]
- menus는 정확히 1개
- message는 영양 상태를 먼저 짚고 추천 음식명을 제안하는 순서로 2문장 이내

[복약 주의]
- cautionNote는 약마다 짧은 한 문장
- 전체를 아우르는 안내 멘트는 만들지 않음
```

```python
# app/config.py
llm_max_output_tokens: int = 700

# app/services/llm.py — OpenAI 호출
body = {
    "model": settings.openai_model,
    "messages": messages,
    "max_tokens": settings.llm_max_output_tokens,
}
```

필요한 정보와 문장 수는 프롬프트에서 직접 줄였고, 예상 밖의 장문을 막기 위해 **700토큰의 안전 상한을 별도로 뒀습니다.** 실제 측정에서는 상한에 도달하지 않았기 때문에 이번 응답 시간 감소를 상한 자체의 효과로 보지는 않았습니다.

OpenAI에는 `max_tokens`, Gemini에는 `maxOutputTokens`, Anthropic에는 `max_tokens`로 같은 상한을 적용해 제공자가 바뀌어도 출력 정책이 유지되도록 했습니다.

## 같은 입력을 변경 전·후 3회씩 실제 호출했습니다

Git 기록에 남은 변경 전 프롬프트와 현재 프롬프트에 **같은 입력과 같은 GPT-4o-mini 모델**을 사용했습니다. 특정 시간대의 영향이 한쪽에만 몰리지 않도록 변경 전·후 호출 순서를 번갈아 실행하고, 소수 측정에서 p95를 계산하는 대신 3회의 중앙값을 비교했습니다.

| API | 출력 토큰 중앙값 | 응답 시간 중앙값 |
|---|---:|---:|
| 다음 끼니 추천 | 119 → **72** | 4.51초 → **1.75초** |
| 복약 주의사항 | 198 → **95** | 2.67초 → **1.87초** |

추천의 출력 토큰은 약 **39%**, 복약 주의는 약 **52%** 줄었습니다. 같은 측정에서 응답 시간 중앙값도 각각 약 **61%**, **30%** 감소했습니다. 현재 프롬프트는 판단 규칙과 예시가 추가돼 입력 토큰은 오히려 늘었지만, 사용자에게 반환하는 출력은 더 짧아졌습니다.

이 결과는 변경 전·후 프롬프트와 설정 전체를 비교한 값입니다. 출력 토큰 수뿐 아니라 프롬프트 구조와 `temperature` 설정도 함께 달라졌고 외부 API의 네트워크 변동도 있으므로, **응답 시간 감소가 출력 길이 하나만의 효과라고 단정하지 않았습니다.**

## 실제 GPT 호출에서도 출력과 대기 시간이 함께 줄었습니다

같은 입력과 같은 GPT-4o-mini를 사용한 변경 전·후 비교에서 **추천과 복약 안내 모두 출력 토큰과 응답 시간 중앙값이 함께 감소했습니다.**

모델을 교체하지 않고도 **사용자에게 필요한 정보의 범위를 먼저 정리하는 방식으로 응답 시간을 개선할 여지가 있음**을 확인했습니다. 다만 프롬프트 구조와 설정도 함께 변경된 비교이므로, 응답 시간 감소를 출력 토큰 하나의 효과로만 해석하지 않았습니다.

> 이번 측정은 조건별 3회에 한정했으며, 더 안정적인 성능 지표가 필요해지면 반복 횟수를 늘려 시간대별 편차와 p95까지 확인할 계획입니다.
