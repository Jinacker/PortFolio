# GPT Vision 건당 비용 12배 절감

> 어르신이 식사할 때마다 사진을 올립니다. 1일 3~4끼 × 사용자 수만큼 Vision이 호출되는데 —
> **아무도 건당 비용을 몰랐습니다.** 대시보드의 월 합계만 있었고, 그게 분석 때문인지
> 문구 생성 때문인지도 구분되지 않았습니다.

## 추정하지 않고 측정했다

서버와 **완전히 동일한 경로**(다운로드 → EXIF 처리 → 1280px 리사이즈 → JPEG base64)로 처리한 뒤
실제 API를 호출해 `usage`를 읽는 측정 스크립트를 만들었습니다.

- 입력 **37,009 토큰** / 출력 33 토큰 → **건당 8.08원**
- 비용의 거의 전부가 **이미지 입력 토큰** — 출력은 JSON 몇십 토큰뿐

## 선택 — 해상도가 아니라 상세도

| 후보 | 판단 |
|---|---|
| 해상도를 768px로 축소 | **토큰이 거의 안 줄어든다** — 타일 계산 방식이라 해상도에 비례하지 않음 |
| **`detail: low` 적용** | 저해상 고정치로 취급되어 토큰이 타일 수와 무관하게 고정 |

선택 기준은 "우리가 이미지에서 뽑는 정보가 무엇인가"였습니다. 이 파이프라인이 GPT에게 요구하는 것은
**음식 이름과 면적 비중**뿐 — 글자를 읽거나 미세 질감을 판별하지 않습니다.
**저해상도로 충분한 작업에 고해상도 요금을 내고 있었던 것**입니다.

## 결과

| 설정 | 입력 토큰 | 건당 비용 |
|---|---|---|
| `detail` 기본 (1280px) | 37,009 | 약 8.08원 |
| **`detail: low`** | **3,007** | **약 0.68원** |

**로직은 한 줄도 안 고치고 12배가 줄었습니다.** 인식 품질은 동일 사진 confidence 0.9로 유지 확인.

이 수치가 있으니 **자체 모델 전환 손익분기**를 계산할 수 있었습니다 — GPU 인스턴스(T4 24/7,
월 15만~38만원) 대비 **월 약 44만 건**. 절감 전 8원 기준이었다면 월 3.7만 건에서 역전됐을 것이므로,
이 최적화 하나가 "자체 모델을 올려야 한다"는 판단을 한참 뒤로 미뤘습니다.

같은 접근으로 LLM 응답도 최적화했습니다 — 느린 원인을 네트워크로 짐작하지 않고 쪼개 보니
**출력 토큰 생성 시간**이 지배 요인이었고, 프롬프트 간결화 + `max_tokens` 상한으로
**3~4초 → 1.5~2.5초.** 지배 요인이 아닌 레버(커넥션 재사용, 수백 ms)는 뒤로 미뤘습니다.

이후 응답에 usage(토큰·예상 비용)를 실어 **호출마다 대시보드에서 보이게** 했습니다.

## 배운 점

- 비용은 **기능이 아니라 설정에 숨어 있을 수 있다** — 로직 수정 0줄로 12배가 줄었다
- 최적화 전에 **동일 경로로 재현하는 측정 스크립트**부터 만든다
- "싼 것을 골랐다"가 아니라 **"이 작업에 그 품질이 필요한가"** 를 먼저 묻는다
