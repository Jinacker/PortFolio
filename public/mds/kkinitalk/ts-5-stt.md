# 벤더 STT가 음성을 못 읽는다 — 두 번의 실험으로 원인 좁히기

> "음성만 503"에서 컨테이너 포맷까지 좁혀 들어간 진단 과정

## 문제 상황

챗봇 텍스트 대화는 정상인데 **"눌러서 말하기"만 실패**했다.
사용자에게는 "지금은 대화할 수 없어요"만 보였다.

서버 로그에는 벤더의 `503 ENGINE_UNAVAILABLE`. 이 메시지만으로는
**우리가 잘못 보낸 건지, 벤더 엔진이 죽은 건지 구분되지 않는다.**

## 원인 분석 — 가설을 하나씩 잘라내는 실험

추측으로 코드를 고치지 않고 **두 번의 실험**으로 원인을 좁혔다.

**실험 ① — 우리 서버 문제인가, 벤더 문제인가**

우리 서버를 빼고 **벤더 API를 직접 호출**했다. WAV 파일로 → **200 OK**.
→ 벤더 엔진은 살아 있다. **우리가 보내는 것에 문제가 있다.**

**실험 ② — MIME 라벨 문제인가, 컨테이너 문제인가**

여기가 핵심이었다. 앱은 `.m4a`를 보내고 있었다. 두 가지 가능성이 있다.

- (a) 벤더가 `audio/m4a`라는 **라벨**을 거부한다
- (b) 벤더가 AAC **컨테이너 자체**를 못 읽는다

**같은 WAV 바이트를 `audio/m4a`로 라벨링해서** 보냈다.

| 보낸 것 | 결과 |
|---|---|
| WAV(LinearPCM) + `audio/wav` | 200 |
| **같은 WAV 바이트 + `audio/m4a` 라벨** | **200** — MIME은 안 본다 |
| 진짜 m4a(AAC) 컨테이너 | **503** `ENGINE_UNAVAILABLE` |

**컨테이너 자체를 못 읽는다**가 확정됐다. 라벨을 고쳐도 소용없었을 것이다.

근본 원인은 문서에 있었다 — **벤더 문서에 STT 지원 포맷이 명시돼 있지 않았고**,
`expo-audio` 프리셋(`HIGH_QUALITY`·`LOW_QUALITY`)이 **전부 `.m4a`**다.
그대로 붙이면 음성이 통째로 안 된다.

## 선택지 비교

### 서버에서 변환 vs 앱에서 처음부터 WAV

| 후보 | 장점 | 단점 |
|---|---|---|
| 서버에 ffmpeg을 넣어 변환 | 앱 변경 불필요, 구버전 앱도 동작 | **의존성이 늘고 업로드된 음성이 서버 디스크에 떨어진다** — 민감정보 체류 |
| **앱이 LinearPCM WAV로 녹음** | 서버는 그대로 흘려보내기만, 파일이 안 남음 | 프리셋을 못 쓰고 옵션을 직접 지정 |

두 번째를 택했다. **음성 원본은 그 자체가 민감정보**라 서버 디스크에 떨어뜨리지 않는 쪽을 택했다.

**16kHz mono**로 고정했다. 음성 인식은 16kHz면 충분하고(전화 음질보다 높다),
44.1kHz 스테레오로 올리면 **파일이 5~6배 커진다.**
어르신 기기가 셀룰러일 수 있고 **업로드가 곧 대기 시간**이다.
30초 발화 기준 16kHz mono 약 1MB, 44.1kHz 스테레오 약 5MB.

## 🔴 그런데 이 결정은 안드로이드에서 틀렸다

당시 나는 이걸 **"남은 한계"로 적어 두고 확인하지 않았다.**

> *"안드로이드에서 실제로 WAV가 나오는지 검증하지 못했다.
> `outputFormat: 'default'`가 플랫폼에 따라 m4a/3gp를 낼 수 있다."*

**실제로 그랬다.** 안드로이드는 WAV 녹음을 지원하지 않는다.
결과적으로 세 계층이 **전부 라벨만 믿고 있었다.**

```
앱   → 확장자·MIME 을 wav 로 붙인다 (안드로이드는 WAV 를 녹음할 수 없는데도)
서버 → 그 라벨을 그대로 벤더에 넘긴다
벤더 → 415·422 가 아니라 불투명한 503(ENGINE_UNAVAILABLE) 으로만 실패한다
```

AMR-NB/3GP 바이트가 `speech.wav`라는 이름을 달고 올라갔고, **안드로이드 음성 대화는
항상 실패하고 있었다.** 나는 iOS 실기기로만 확인했다.

### 팀원이 서버측 변환으로 해결했다

`audio-format.ts`가 **매직 바이트로 컨테이너를 판별**한다(`RIFF..WAVE` · `#!AMR` ·
`ftyp` 브랜드 · `OggS` · EBML · MP3). WAV면 그대로 통과시키고(iOS 경로, 변환 비용 0),
아니면 ffmpeg으로 16kHz mono PCM WAV로 굽는다.

**내가 서버 변환을 반대한 이유는 다른 방법으로 해결됐다.**
`stdin → stdout` 파이프라 **디스크에 쓰지 않는다.** "음성을 저장하지 않는다"가 유지된다.

내가 못 본 것이 하나 더 있다 — **제약의 주인은 벤더다.**
기기·OS·향후 웹뷰마다 코덱이 다른데 앱에서 맞추면 문제가 생길 때마다 **앱 배포**가 필요하다.
서버면 한 곳에서 흡수한다. 나는 "민감정보"만 보고 "변경 비용"을 안 봤다.

## 결과 — 측정으로 검증

- 실제 한국어 WAV로 STT **200 OK, 3.3초**
- 서버 쪽에서 실패 원인을 **세 가지로 분기**해 메시지를 다르게 했다.
  같은 "음성 파일이 없습니다"가 원인이 여러 개라 디버깅이 오래 걸렸기 때문
  - `audio` 필드 자체가 없음 → "음성이 전달되지 않았어요 (form-data audio 필드 없음)"
  - 파일은 있는데 0바이트 → "녹음된 소리가 없어요"
  - 크기 초과 → 별도 메시지
- 앱에서도 **업로드 전에 파일 크기를 확인**해 1KB 미만이면 벤더를 호출하지 않는다.
  WAV 헤더만 44바이트라 1KB 미만은 사실상 무음
- 벤더 요청 항목에 **"STT 지원 포맷을 문서에 명시해 달라"** 를 등록

## 남은 한계

- **안드로이드 실기기 확인을 안 하고 결정을 내렸다.** 그리고 그 결정이 틀렸다.
  "한계로 적어 뒀으니 됐다"고 넘어간 것이 문제였다 — **적는 것과 확인하는 것은 다르다**
- 벤더가 **지원 포맷 목록을 아직 안 줬다.** WAV가 되는 것만 알고 다른 포맷은 모른다
- 최종 해법(서버측 변환)은 **팀원이 만들었다.** 내 몫은 원인 진단(컨테이너 문제)까지였다

## 배운 점

- 에러 메시지가 **원인을 구분해 주지 않으면 실험으로 구분해야 한다는 것.**
  "우리인가 벤더인가" → "라벨인가 컨테이너인가" 두 번의 이분법으로 좁혔다
- **같은 바이트를 다른 라벨로 보내는 것**처럼, 변수를 하나만 바꾸는 실험 설계가 핵심이라는 것
- 서버 에러 메시지는 **원인별로 달라야 한다는 것.** 하나로 뭉뚱그리면 다음 사람이 같은 시간을 쓴다
- **한계를 적는 것과 확인하는 것은 다르다는 것.** "안드로이드 미검증"이라고 써 놓고
  넘어갔는데, 그게 바로 결함이었다. 적어 둔 덕에 다음 사람이 찾긴 했지만
  **적기만 하면 그건 인계이지 해결이 아니다**
- 반대 이유가 **다른 방법으로 해소될 수 있는지 먼저 찾아야 한다는 것.**
  나는 "서버 변환 = 디스크에 음성이 남는다"로 후보를 잘랐는데,
  `stdin→stdout` 파이프면 안 남는다. **제약을 조건으로 보지 않고 결론으로 썼다**
