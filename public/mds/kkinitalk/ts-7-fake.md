# 운영에서 가짜 AI가 사용자에게 응답했다

> 테스트 366개가 통과하는 동안 화면에 `[fake stt] 74862바이트`가 떴다

## 문제 상황

챗봇 어댑터를 개발할 때, 벤더 없이도 개발·테스트가 되도록 **가짜(fake) 어댑터**를 만들고
환경변수로 전환하게 했다. 흔한 패턴이고, AI 서버에서도 같은 패턴을 쓰고 있었다.

배포에 `CHATBOT_TOKEN`이 없었다. 그래서 **기본값인 `fake`가 실제 사용자에게 서비스됐다.**

발견은 **사용자 제보**였다. 화면에 `[fake stt] 74862바이트` 같은 문구가 떴다.

## 왜 아무 알람도 안 울렸나

| 지표 | 상태 |
|---|---|
| HTTP 상태 코드 | **200** |
| 에러 로그 | **0건** |
| Jest | **366 passed** |
| 배포 | **성공** |

**전부 초록이었다.** 가짜 어댑터는 정상적으로 가짜 응답을 만들어 200으로 돌려주고 있었기 때문이다.

관측 가능한 모든 지표가 "정상"을 가리키는데 사용자는 가짜 응답을 받고 있었다.
**이건 모니터링으로 잡을 수 있는 종류의 사고가 아니다.**

## 원인 분석 — 내 설계 결정이 원인이었다

**안전한 기본값을 잘못 골랐다.**

AI 서버에서 "키가 없어도 서버는 떠야 한다"는 원칙을 세웠고(구현 3), 그건 옳았다.
개발·CI·대시보드가 키 없이 돌아야 하니까. 그 원칙을 챗봇에도 그대로 가져왔다.

그런데 **AI 서버의 mock은 대시보드에 "mock(무료)"이라고 표시되고 개발자만 본다.**
챗봇의 fake는 **어르신 화면에 그대로 나갔다.**

같은 패턴인데 **소비자가 달랐다.** 기본값이 빠졌을 때의 동작을
"동작하지만 틀림"으로 뒀는데, 그게 운영까지 따라갔다.

## 선택지 비교

| 후보 | 판단 |
|---|---|
| 배포 체크리스트에 환경변수 항목 추가 | **사람이 빠뜨린다.** 이번에도 그래서 났다 |
| 부팅 시 키를 검사하고 없으면 기동 실패 | 안전하지만 **개발·CI가 막힌다** |
| **운영 환경에서만 가짜 어댑터가 503을 던지게** | 개발은 그대로, 운영에서는 시끄럽게 멈춤 |

세 번째. `isProduction`이면 모든 메서드가 **즉시 예외를 던지고 부팅 시 에러 로그**를 남긴다.

**절차로 못 막으면 코드가 막아야 한다.**
사람이 체크리스트를 빠뜨리는 것보다 **부팅이 실패하는 게 낫다.**

여기에 벤더 어댑터의 **부팅 자가진단**도 추가했다.
기동 시 토큰으로 usage를 조회해 연결 가능 여부를 로그로 남긴다.
**첫 사용자 요청이 아니라 부팅 시점에** 알 수 있어야 한다.

## 결과 — 측정으로 검증

- 가짜 어댑터의 **8개 메서드 전부 운영에서 503**을 반환하는 것을 테스트로 고정
- 부팅 자가진단 로그 — 연결 성공 시 이달 사용 토큰까지 표시
- **원칙을 문서에 명문화** — *"기본값은 '동작하지만 틀림'이 아니라 '동작하지 않음'이어야 한다"*
- `Jest 377 passed`

## 남은 한계

- **같은 패턴이 AI 서버에도 있다.** mock 백엔드는 여전히 기본값이다.
  소비자가 개발자뿐이라 위험도가 낮다고 판단했지만, 같은 사고가 안 난다는 보장은 없다
- 배포 환경변수 검증이 **부팅 로그 수준**이다. 필수 항목 누락을 기동 실패로 만들지는 않았다

## 배운 점

- **자동 지표가 전부 초록인 것이 안전을 뜻하지 않는다는 것.** 이 사고는 200·에러 0·테스트 통과
  상태로 일어났다
- **기본값은 "동작하지만 틀림"이 아니라 "동작하지 않음"이어야 한다는 것.**
  조용히 틀리는 것보다 시끄럽게 멈추는 게 낫다
- 같은 패턴도 **소비자가 다르면 위험도가 다르다는 것.** 개발자가 보는 mock과
  어르신이 보는 fake는 같은 코드 구조라도 전혀 다른 문제다
